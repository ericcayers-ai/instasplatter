# Research: GitHub ecosystem sweep part C — VISUAL POSITIONING SYSTEMS (VPS), visual localisation against Gaussian splats, and geospatial place recognition

_Research date: 2026-11-03. All stars / licenses / last-push timestamps were pulled the same day from per-repo JSON metadata (`ungh.cc` mirror of the GitHub repos API + `img.shields.io/github/license/*.json`, both of which proxy `api.github.com`). `api.github.com` itself was rate-limited from this host (HTTP 403, shared IP), so **no number below is from memory** — anything I could not pull is written "not verified"._

_Accuracy figures are **quoted from papers/READMEs, never measured here**. Where a number reached me only through a secondary summary (a paper table quoted by a third party), it is marked as such._

---

## Summary

The ecosystem splits cleanly into three layers, and instasplatter's `src/geospatial/vps.ts` currently implements a 2015-era version of the *middle* layer while getting the *architecture* right. For (A) ground-level phone-in-a-splat localisation, the published SOTA is now **splat-grounded 2D–3D keypoint descriptors** (SplatLoc, GSplatLoc, Splat-Nav/Splat-Loc) layered on the classic **hloc** retrieval→2D-2D→PnP recipe, with median errors of **1–3 cm indoor / ~17–27 cm outdoor** quoted in those papers. For (B) geospatial/wide-area positioning, the SOTA shifted to **MegaLoc-class retrieval** (92.6 R@1 on MSLS-val, quoted) plus a georeferenced database — global-descriptor-only, not PnP. `vps.ts`'s four-stage skeleton (coarse retrieval → 2D–3D match → PnP+RANSAC → ENU/WGS84) is therefore **directionally sound and matches the hloc/SplatLoc family**, but four components are outdated or defective: NetVLAD-class retrieval instead of MegaLoc/SALAD, direct descriptor lookup into splat anchors instead of 2D–2D matching against keyframes, a hand-rolled non-randomised "RANSAC" instead of PoseLib/MAGSAC++-class estimators, and heuristic HDOP/VDOP instead of a propagated covariance. There is also a **probable sign error in the analytic rotation Jacobian** of `refinePoseLevenbergMarquardt` (researcher inference from the code, needs a numerical-Jacobian test), and the docstring advertises viewing-ray cone gating that the code does not implement.

## Findings

### F0. State of the existing implementation (`src/geospatial/vps.ts`, 852 lines)

1. **Claim:** `vps.ts` is a self-contained, dependency-free TS pipeline: `retrieveCandidateVpsSubmaps` (cosine on one global descriptor + optional WGS84 prior with `exp(-d/…)` weighting, 0.65/0.35 blend) → `matchQueryToSplatAnchors` (brute-force L2 + Lowe ratio 0.8 + mutual-NN + `maxDescriptorDist` 0.9) → `solvePnpRansac6DoF` (7 centroid-offset hypotheses × ≤3 subsets, damped Gauss-Newton/LM, 6 px threshold) → `enuToWgs84` + heading/pitch/roll + heuristic `hdopM`/`vdopM`. **Sources:** direct read of the file. **Support:** direct evidence (file contents). **Confidence:** high.
2. **Claim:** The rotation block of the analytic Jacobian in `refinePoseLevenbergMarquardt` appears to have a **flipped sign**. With `x_cam = R(X−C)` and a *left* perturbation `R' = exp([ω]×)R` (which is what `applySmallRotation` does), the correct derivative is `∂P_cam/∂ω = −[P_cam]×`; the code emits `Ju = [+du_dZ·Y, du_dX·Z − du_dZ·X, −du_dX·Y]` and `Jv` analogously, all three of which are the negation of that. Translation columns (`−(du_dX·R[0] + du_dZ·R[6])`, …) are correct. **Sources:** `src/geospatial/vps.ts` lines defining `Ju`/`Jv` + standard left-perturbation derivation. **Support:** researcher inference (analytic, not executed). **Confidence:** medium-high. **Impact:** LM would under-correct rotation and lean on damping; final polish quality is suspect. Must be validated with a numerical-Jacobian / finite-difference test before any adoption.
3. **Claim:** "RANSAC" is not RANSAC. There is no random minimal-set sampling, no P3P/EPnP minimal solver, and the 3 "subsets" are 4 *consecutive* matches (spatially correlated), so outlier rejection is essentially a fixed-hypothesis grid search. **Sources:** file. **Support:** direct evidence. **Confidence:** high.
4. **Claim:** The header comment promises "viewing-ray cone gating" in stage 2, but `matchQueryToSplatAnchors` contains no cone/visibility test (it accepts `normalEnu` on `SplatAnchor3D` but never reads it). `solve3x3` is dead code kept alive by `void solve3x3;`. **Sources:** file. **Support:** direct evidence. **Confidence:** high.
5. **Claim:** `hdopM`/`vdopM` are `(medianReprojectionErrorPx + 0.25)/√n × {0.45, 0.65}` rounded to 3 dp — not metres, not a covariance, and not a DOP in the geodetic sense. `confidence` thresholds (≥6 inliers & <2 px, ≥4 & <5 px) are arbitrary. **Sources:** file. **Support:** direct evidence. **Confidence:** high.
6. **Claim:** `vps.ts` performs no feature extraction, no 2D–2D matching, and stores descriptors on splat "anchors" — i.e. the hardest part of problem (A) (getting reliable 2D↔3D correspondences from a phone photo) is assumed, not implemented. **Sources:** file (types `QueryKeypoint2D`, `SplatAnchor3D`). **Support:** direct evidence + inference about caller burden. **Confidence:** high.
7. **Claim:** The file is not imported anywhere and has no tests. **Sources:** task brief. **Support:** direct evidence from brief; **I could not independently grep the repo** (no shell in this session). **Confidence:** medium.

## Verdict on `src/geospatial/vps.ts` (6 lines)

1. **Architecture: sound, keep it.** Coarse-to-fine → 2D–3D → robust PnP → ENU/WGS84 is exactly the hloc/SplatLoc-family decomposition; splitting ground and geospatial domains behind one interface is defensible and matches how the literature separates retrieval from metric pose.
2. **Retrieval: outdated.** A single cosine-scored global descriptor described as "NetVLAD / GeoCLIP / StreetCLIP" is a 2015–2023 mix; swap to MegaLoc (or CosPlace as the cheap fallback) and add re-ranking of top-k — the 0.65/0.35 geo-prior blend otherwise hides retrieval failure instead of exposing it.
3. **Matching: wrong level of abstraction.** Direct query-descriptor → splat-anchor lookup with Lowe+mNN is far weaker than hloc's 2D–2D-against-keyframes-then-lift and than SplatLoc/GSplatLoc's *learned* descriptor grounding; also the docstring's "viewing-ray cone gating" is not implemented, so occluded/back-facing anchors are matched freely.
4. **Solver: replace, don't patch.** No random minimal sampling, no P3P, 4-consecutive-match "hypotheses", and a **probable rotation-Jacobian sign error** in the LM refinement (analytic inference; must be numerically tested) mean the reported quality is not defensible — move to PoseLib/OpenCV-class PnP + MAGSAC++/GC-RANSAC.
5. **Uncertainty: overclaims.** `hdopM`/`vdopM` and the "high/medium/low" confidence are hand-tuned scalars, not propagated covariance; a VPS that reports metres must compute a pose covariance from the inlier reprojection Hessian (or bootstrap the inliers) — otherwise delete the fields rather than publish pseudo-DOPs.
6. **Scope: A is under-served, B needs a different tack.** There is no feature extraction, no client-side path, and no metric-scale handling for the phone case (Depth Anything V2 / Metric3D solve that), while the aerial case needs ground↔satellite cross-view retrieval (Sample4Geo/SUES-200) and glim-style georeferenced submaps — a single "hybrid" descriptor space will not span both; split by domain, keep one interface.

## Contradictions

1. **CosPlace on MSLS.** Original CVPR'22 paper: R@1 **79.6**, R@5 87.2 (512-D, SF-XL). MegaLoc's Table 1: CosPlace **85.0/92.6** on MSLS-val. EigenPlaces' table: **86.9** R@1 (ResNet-50). Three different numbers for "the same method+dataset" — split/protocol differences (MSLS challenge vs val, backbone, descriptor dim). Not resolved here; anyone quoting "CosPlace 85" should say "MSLS-val".
2. **AnyLoc on MSLS.** MegaLoc's table lists AnyLoc at MSLS-val **58.7/74.5**, while Revisit-Anything-derived figures give **83.4** (MSLS-SF) / **79.9** (MSLS-CPH). An ~25-point gap cannot be protocol noise alone — likely different aggregation variants / evaluation scripts. **Do not cite AnyLoc's MSLS number** without pinning the variant.
3. **hloc on Cambridge.** README per-scene table averages ≈11 cm / 0.2°; an independent leaderboard records **10 cm / 0.2°**. Minor, but confirms that quoted medians depend on the eval harness.
4. **GSplatLoc benchmarks.** One search summary claimed GSplatLoc reports Replica/TUM numbers; the paper's own project page says 7Scenes + Cambridge (+ Phototourism, Sitcoms3D). The Replica/TUM claim belongs to **SplatLoc**, not GSplatLoc. Recorded and resolved in favour of the project page.
5. **6DGS evaluation set.** 6DGS is frequently discussed alongside Replica/12-Scenes localisation (that is SplatLoc's territory); the ECCV'24 paper actually evaluates Tanks & Temples and Mip-NeRF 360°. Its mean angular errors (~21.7°/~24.3°, quoted from a *later comparison paper*, not the original) are therefore not comparable with SplatLoc's 0.1–0.6°.
